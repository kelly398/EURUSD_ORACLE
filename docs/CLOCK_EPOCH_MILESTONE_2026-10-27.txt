EVIDENCE AND CLOCK CONVENTION

The connected broker company is HFM Investments Ltd. The initial diagnostic
recognized other HFM aliases but omitted this company name; that diagnostic was
corrected. The actual policy binds exact company/server fingerprints, rather
than relying on a company-name substring or the worker's printed HFM label.
Account identifiers, balances, credentials and server names were not stored.

Repeated live observations showed raw labels about two hours ahead of UTC.
Separate short history requests established that the query parameters also use
broker-wall-clock labels on this server: querying the unshifted UTC interval
returned an older interval, while broker-clock queries returned current data.
Both parameter conversion and payload conversion are therefore necessary.

HFM publishes winter GMT+2 / summer GMT+3 and changes on the last Sundays of
March/October:
  https://www.hfm.com/int/en/trading-instruments/trading-hours
The generic MetaTrader Python documentation describes UTC instead:
  https://www.mql5.com/en/docs/python_metatrader5/mt5copyticksrange_py
The implementation uses the observed server behavior and the explicit broker
policy, with validation on each read. It does not apply this convention to every
MT5 broker or infer offsets from the host's timezone.

The policy and its original probe evidence are saved together:
  docs/clock_profiles/hfm_forward_20261027.json
  docs/clock_profiles/hfm_probe_evidence_20261027.json
Their evidence hash matches. The policy binds conversion source-code bytes,
company/server fingerprints and an expiring forward interval. Its current end is

Source-code changes, lease expiry, broker/server changes, invalid quote clocks,

IMPLEMENTATION

backend/data_engine/clock_policy.py implements deterministic HFM seasonal-date
rules. It preserves exact milliseconds and rejects the first six local hours on
seasonal transition Sundays, including ambiguous/nonexistent labels. HFM's page
does not specify an exact intraday cutover, so those labels are not guessed.
Requests are bounded and cannot span a seasonal clock change without splitting.

The existing MT5Provider accepts an optional typed clock policy. Without one,
its original UTC quarantine behavior remains. With one, it checks the actual
broker identity, converts both request bounds and returned records, retains the
raw source fields, filters inclusive endpoint excess and refuses responses from
a different time convention. Existing quote freshness/future-clock bounds remain.

Both legacy ingestors explicitly refuse clock-normalized providers, preventing
accidental writes into the unversioned archive. New storage is isolated in:
  oracle_utc_feed_schema
  oracle_utc_feed_epochs
  oracle_utc_feed_captures
  oracle_utc_ticks
  oracle_utc_bars

The forward store preserves raw records, UTC event times, source receipts and
actual ingestion times. A full capture commits atomically. Duplicate ticks/bars
retain their first receipt. A changed closed bar is rejected pending explicit
revision handling; it cannot silently overwrite an earlier observation.

The recorder uses UTC wall time for completed-bar boundaries. Recovery uses a
durable completed-query cursor, including empty intervals, rather than assuming
that the last tick proves how far a query progressed. Repair overlap covers the
existing quote-age/future tolerances. Gaps recover through bounded windows;
failed requests do not advance the cursor and unqueried intervals cannot be
silently skipped after capture has begun.

One process owner remains: market_data_supervisor.py accepts --clock-policy and
runs one managed UTC recorder instead of the legacy pair. The recorder supports
continuous operation under that supervisor and handles its shutdown signal.
The legacy default is retained explicitly; it does not silently switch datasets.

ARCHIVE ANALYSIS

Five samples across both seasonal boundaries matched stored OHLC to the same raw
MT5 bar labels, and sampled tick timestamps equalled raw source-clock values.
Then all 75,528 legacy M5 candles were scanned read-only under the candidate
seasonal mapping:

  44,512 would shift by three hours; 31,016 by two hours.
  Zero candidate conversion rejections, duplicate UTC timestamps or nonmonotonic
  UTC timestamps were found.
  Zero OHLC/completion errors were found by this scan.
  45,691 would change their active-session classification.
  1,644 would change the existing engine's NY-based market-open classification.

These are candidate results using current published seasonal rules, not proof
of the broker's entire historical publication record. No legacy rows were
rewritten or given a historical UTC certificate. Its latest stored tick remains
2026-10-07 16:31:14.973 in the original label domain.

The price history remains useful. Relative price-return labels may remain valid
within constant-offset periods, but absolute-time features, sessions, split
boundaries and cross-source macro alignment need a versioned reconstruction and
evaluation. Frozen v1 results describe their original dataset and time convention;
they do not automatically validate models on corrected UTC features.

OPERATING COMMAND

Use the existing supervisor in the explicit UTC mode:
  .\oracle_env\Scripts\python.exe -m backend.runtime.market_data_supervisor --clock-policy docs/clock_profiles/hfm_forward_20261027.json

For a bounded run, add --run-seconds 60. The new tables are already initialized.
The individual capture command also supports --initialize for a fresh database;
that operation creates only its own isolated tables.

REMAINING WORK

The new epoch is an observational input foundation, not full Council readiness.
Its bar history is still short and is not automatically injected into the live
Council. Existing consumers retain their legacy source until the clock-aware
feature/model contract is installed. No mixed-clock dataset is presented as PASS.

Next create an explicit historical research reconstruction and a new feature/
dataset version, preserving source times and uncertainty. Extend artifact
compatibility to include clock convention and source epoch. Evaluate the effect
before promoting new model versions; do not reuse the consumed v1 reserved tests
as a new untouched holdout. Wire the normalized source into shadow decision and
outcome collection with actual receipt availability, then evaluate adaptive
weights against fixed baselines after costs.

Unattended operation still needs policy renewal, monitoring/alerts, revision
versioning, storage sizing/retention and backup/restore testing. A worker failing
closed is deliberate; it does not by itself implement a complete operational
recovery policy. Financial execution and source-admission gates remain separate.
